    explanation: Diagnosing which stage failed is the key skill; end-to-end scores alone hide it.
  - id: diagnose
    prompt: An answer is wrong. What should you check first?
    options:
      - text: Switch to a larger LLM
      - id: retrieval
        text: Whether the retrieved chunks contained the correct information — separating retrieval failure from generation failure
        correct: true
      - text: Increase temperature
      - text: Add more documents
    explanation: Most production RAG errors are retrieval errors. A bigger model cannot answer from absent evidence.
  - id: retrieval-metrics
    prompt: Which metrics evaluate the retrieval stage?
    type: multiple
    options:
      - id: recall
        text: Recall@k — whether the relevant chunks appear in the top k
        correct: true
      - id: precision
        text: Precision / context relevance — how much of the retrieved context is relevant
        correct: true
      - id: mrr
        text: Mean reciprocal rank — how high the first relevant result ranks
        correct: true
      - text: BLEU score of the final answer
    explanation: These need labelled question–relevant-chunk pairs, which you can bootstrap with an LLM and review by hand.
  - id: stale
    prompt: A policy was updated last month but the bot quotes the old version. Likely cause?
    options:
      - text: The LLM is too old
      - text: Temperature is too high
      - id: stale-index
        text: The index was not refreshed, or old and new versions both remain indexed without date metadata or deduplication
        correct: true
      - text: The user asked incorrectly
    explanation: Index freshness and document lifecycle (deletes, supersessions) are data-engineering problems.
  - id: poisoning
    prompt: Anyone in the company can edit the wiki that feeds your RAG bot. What risk does this create?
    options:
      - text: None
      - id: poison
        text: Knowledge poisoning and indirect prompt injection — a malicious or careless edit becomes an authoritative-sounding answer or an instruction to the model
        correct: true
      - text: Faster answers
      - text: Higher recall
    explanation: Curate sources by trust level; show citations so users can judge.
  - id: permission-leak
    prompt: A RAG bot answers a question about executive salaries for a junior employee. What design failure occurred?
    options:
      - text: The LLM was too smart
      - text: The chunk size was wrong
      - text: The embedding model was outdated
      - id: no-acl
        text: Retrieval did not enforce document-level permissions for the asking user
        correct: true
    explanation: Filter by the user's entitlements at retrieval time. Never rely on the LLM to "keep secrets".
  - id: multi-hop
    prompt: Why do questions like "Which of our customers in Germany use the product that had the 2025 recall?" challenge simple RAG?
    options:
      - id: multi-hop
        text: They require combining facts from several documents or structured data (multi-hop), which a single similarity search rarely retrieves together
        correct: true
      - text: German is not supported
      - text: They are too short
      - text: Dates cannot be embedded
    explanation: Agentic retrieval (iterative search), SQL over structured data, or knowledge graphs (GraphRAG) can help.
  - id: graphrag
    prompt: What is GraphRAG?
    options:
      - text: Charts generated by RAG
      - text: A graph database for vectors only
      - id: graph
        text: An approach (popularised by Microsoft Research, 2024) that builds a knowledge graph and community summaries from documents to answer global or multi-hop questions
        correct: true
      - text: A visual debugger
    explanation: It costs much more to index and is worth it only for questions plain RAG cannot handle.
  - id: aggregate-q
    prompt: "A user asks a document bot: \"How many contracts expire in 2027?\" Why might RAG answer badly?"
    options:
      - text: The number is too large
      - text: Contracts cannot be embedded
      - id: aggregation
        text: Counting requires scanning all contracts, but RAG retrieves only top-k chunks; extracting fields into a table and using SQL is the right design
        correct: true
      - text: RAG does not support years
    explanation: Know when a question is a database query in disguise.

## Learning objectives

- Diagnose RAG failures by stage
- Measure retrieval quality
- Recognise poisoning, permission leaks and aggregation questions

## A diagnostic table

| Symptom | Likely stage | Fix |
|---|---|---|
| "I can't find that" but the doc exists | Retrieval | Hybrid search, query rewriting, chunking |
| Wrong answer, right chunk retrieved | Generation | Prompt, model, context ordering |
| Outdated answer | Indexing | Refresh, versioning, dedup |
| Garbled numbers | Parsing | Layout-aware parsing |
| Leaked document | Access control | Permission filters at retrieval |
| Counting/aggregation wrong | Design | Structured extraction + SQL |
